# R19 采样与源机登记计数衔接：离线修复

本轮仅按用户授权进行离线定位、修复和回归。没有部署、建机、重跑 R19、连接正式环境或操作 tanzhen；自动开关未修改。本记录不把 [R19 未通过的原始结论](machine-r19-result-20261114.md) 改写成通过。

## 历史事实与复现边界

R19 源机窗口在 23:06:16、23:06:27、23:06:38 记录了失败计数 1、2、3，最后一次达到阈值；随后的登记却拒绝了 `threshold_reached` 和 `observed_failures`。其余 28 项检查通过。原始字段首错没有记录登记瞬间的具体计数，不能补写为 1 或 2，也不能声称已唯一还原当时的计数变化路径。

离线确认了一条足以产生同样分歧的代码路径：

1. 控制端采样完成后，登记函数先执行云资源 `reconcile`。这次读回没有同时运行连续观察。
2. 观察器按原有规则，在相邻样本超过 `interval * 2 + 10` 时重置计数。配置间隔 5 秒时，连续性边界仍是 20 秒；重置是必要保护，不是应被取消的错误。
3. 旧登记代码只再观察 5 次，每次间隔 5 秒，实际等待窗口约 20 秒。按本轮实际采样中出现的 11 秒上报节奏，重新取得 3 个独立失败报告可能需要 22 秒并在下一次轮询才读到，短窗口会提前拒绝。

使用内存 SQLite、真实 `MachineAddressInventory` / `MachineFailoverObserver` 和虚拟时钟模拟 33 秒断档：旧计数正确从 5 重置为 1，原短窗口最终只有 2，重现 R19 的两个拒绝字段。新窗口在第 6 次观察、25 秒时重新收齐 3 次才通过。这里的 33 秒、计数 2 和 25 秒均为隔离夹具结果，不是补写的 R19 历史观测值。

## 修复

- 改动限于 `tools/machine-acceptance` 的登记/诊断工具和测试，没有修改业务观察器、模型、队列、节点程序或默认配置。
- 云归属读回后，在单调时钟及墙钟双重约束下，最多 60 秒、12 次控制端观察；不再重试云创建或轮换凭证。慢读取已经消耗的时间不会再额外叠加 5 秒等待。
- 不延长观察器的 20 秒连续性边界，不把采样窗口旧计数转交为新授权。仍至少需要 3 次当前失败；策略阈值更高时保留更高阈值。
- 核对真实观察行与摘要属于相同策略版本、上下文及样本，两个计数必须一致。公开观察模型隐藏了 `context_key`，因此只在本地按精确观察 ID 读取不可变行作比较，不将该键导出。
- 登记前再次读取当前摘要并与合格窗口核对。新报告、恢复、上下文变化或未收集状态不能借用窗口刚才的计数通过。
- 循环及写入前检查本轮授权、停止和有效期。超时、未知、恢复、重复旧报告及时钟异常均保持拒绝；超时之后才读到第 3 次失败也不得通过。

## 字段级诊断与首错

原有纯字段检查器及 schema 1 仍可读取；新的登记拒绝使用 schema 2，增加：

- 最少失败数、60 秒预算、5 秒节奏、停止原因及最多 12 个观察步骤。
- 每步的观察行计数、摘要计数、两个样本时间、当前性、阈值及上下文/样本匹配布尔值。
- 登记瞬间的具体计数、样本时间、当前性、阈值和上下文一致性。
- `observation_window_complete` 字段，明确区分“曾达到阈值”和“当前、限时窗口仍合格”。

所有字段均有白名单、严格类型和数量/数值界限，不包含真实用户信息、IP、配置正文、凭据、上下文键、原始错误文本或堆栈。PHP 与 Python 的解析规则通过同批正负样本核对。

控制端日志封装固定 schema 1，新字段诊断改为嵌套保存，防止 PHP 数组联合覆盖内部 schema 2。新的 `source_journal()` 同时支持旧平铺记录及新嵌套记录，并核对轮次和应用版本。

本地通用 CLI 首错格式不变；完整源机字段诊断另存 `source-fixture-first-error.json`。二者均独占创建、限制权限/大小并独立读回；后来的计数或保存失败不能覆盖首次诊断或冒充已保存。

新增只读绑定检查：带新计数窗口的适配器必须让清理收集器调用规范的 `cli_error_capture.source_journal()`；若存在独立源诊断投影，则必须使用规范的 `cli_error_capture.fields()`。缺失或仍只识别旧结构时，冻结预检阶段就拒绝，不能等建机后才发现导出不兼容。没有修改任何旧轮收集器或运行旧轮入口。
