# 代理代收资金安全复查

复查日期：2026-09-14。审查基线：`68e39759733edb84816e5bfd03e2b01a7e1c76c9`。

本记录是代码及隔离测试结论，不是线上支付验收或零亏损承诺。以下修复应与本记录一起部署；仅部署上述基线提交不包含本次修复。本次没有操作线上数据、创建真实支付或发起提现。

## 发现与修复

### 1. 退款处置与履约重试交错

- 已支付但仍在处理的订单可以先被退款处置，随后旧履约任务重试。
- 原代码实测会重新生成充值本金记录，或继续延长套餐；原有不计退款利润的检查没有阻止交付本身。
- 修复：锁定订单后检查退款标记，退款订单不再履约；代收充值入账服务也独立拒绝退款来源。
- 回归使用真实退款处置服务，分别覆盖充值与套餐，并连续重试两次。修复前两项失败，修复后本金、普通余额、利润和套餐有效期均不增加。

### 2. 升级确认过早读取订单快照

- 原流程在锁定买家前读取未完成订单；MySQL 可重复读事务可能固定旧快照，等待账户锁后再次普通查询不等于最新数据。
- 修复：事务首先锁定买家，再读取报价和订单，串行检查本买家的升级条件。
- 回归检查实际查询顺序，修复前订单读取早于账户读取，修复后顺序正确。SQLite 无法证明真实 MySQL 锁等待行为，不能把此回归称为并发验收。
- 依据：[MySQL 一致性读取](https://dev.mysql.com/doc/refman/8.4/en/innodb-consistent-read.html)、[MySQL 锁定读取](https://dev.mysql.com/doc/refman/8.4/en/innodb-locking-reads.html)。

### 3. 负手续费导致代收少收多记

- 历史支付配置允许负固定手续费。代收本金按订单金额入账，外部应收却减掉负费用，可能形成缺口。
- 修复：代收结账拒绝负手续费；支付确认和入账资金验证也拒绝历史负手续费订单。其他模式原有配置不在此次变更范围内。
- 两项失败回归分别证明原代码会接受新负手续费结账和旧负手续费订单入账；修复后失败操作不写入本金或利润。

### 4. 回调校验与入账之间的状态变化

- 原回调先读取订单并验款，付款服务之后再次读取订单，但没有使用真实回调金额和渠道复核第二次读取结果。
- 交错测试分别在两次读取间修改金额、渠道、手续费，原代码三项均错误放行。
- 修复：真实回调将渠道和实收金额传入付款事务，在订单锁内再次校验。纯余额付款和自动续费也在锁内要求应付仍为零。
- 同时拒绝无渠道身份、布尔值、数组、空值、带后缀金额及小数分；支持非负整数分和合法整数字符串，不再强制截断非法值。
- 无法核对的回调返回失败并保留订单，不会根据错误凭证增加余额。渠道更换后旧渠道付款等异常仍需人工核实真实收款，不能丢弃或直接删除订单。
