# 故障转移生产接管

目标是让 keliboard 能在指定服务的维护窗口内接替 tanzhen，并能在失败时安全交还。**当前未达到生产待命标准。本文不是部署、建机、修改 DNS 或接管的授权。**

## 本地授权与派发

[授权服务](../../../app/Services/ServerMachine/Cloud/MachineFailoverHandover.php)已接到原生意图和独立运行器的内部路径，并通过本地及隔离 Linux 验证。生产硬锁保持拒绝，未新增管理端或 CLI 签发入口，也未在正式环境执行迁移。

- 同一时间只保留一个服务的接管名额。一份授权最长两小时，最多绑定一次原生执行；单次执行仍不得超过原有的 20 分钟上限，也不得晚于授权到期。绑定现有服务快照指纹（含成员策略、凭证和 DNS 修订）、操作者、V2 流程与节点包哈希。生产应用镜像摘要仍要由发布关卡确认。
- 接管授权与原意图同事务绑定，再入队。派发、工作器及写入记录边界从主数据库读回同一授权，不信任队列快照；错服务、到期、撤销、身份或版本漂移、另有执行未核清时拒绝新工作。租约或授权检查不跨外部请求持有数据库锁。
- 撤销先于派发记录提交时，阻止该操作。派发记录已提交时，外部操作可能在途，即使未收到回执也保留原意图和审计，不重发。运行器完成本地停止后，[内部读回](../../../app/Services/ServerMachine/Cloud/MachineFailoverHandoverRecovery.php)可按原身份核对候选创建、记录集或单条 DNS 修改；仅返回脱敏结果和摘要，不做写入、接纳候选、认领记录或结案。云的列表未找到不代表不存在；单次精确 404 不等于已确认清理。
- 名额不会因为到期、撤销或一次读回自动释放。只有尚未绑定执行的授权可以显式释放；已绑定的授权仍需正式的核查结案与释放流程。旧交接证据不能重用于签发新授权。
- 授权记录只保存已审交接材料的摘要，**不证明 tanzhen 已停写**。后续签发入口必须核对交接证据，不可从浏览器、自报状态或配置开关推断单写者。

## 隔离并发验收

2026-11-18 在临时验收分支手动运行[隔离工作流](https://github.com/keli-123456/keliboard/actions/runs/44223392866)，测试快照为 `c601e24db35999e0acfc8c6a72c596d92373a172`。Linux 下运行真实 MySQL 8.4/InnoDB、Redis 7、独立队列工作器和回环 HTTP；云平台和 DNS 为模拟，不连接正式环境。`REPEATABLE READ` 和 `READ COMMITTED` 两组各通过 31 项、695 条断言，无失败、错误或跳过；两组各 26 条并发用例均有清理记录。

| 撤销时机 | 两种隔离级别结果一致 |
| --- | --- |
| 云创建派发前 | 0 次模拟创建，原任务没有派发记录。 |
| 云创建已发、工作器退出 | 仅原来的 1 次模拟创建。停止后只读回原资源，不补发，不释放接管名额。 |
| 双栈 DNS 写入前 | 0 次模拟 DNS 写入。子任务保留 `handover_revoked`，动作仍为待派发且没有写入记录，租约已清空。 |

## 待命关卡

下列关卡全部有证据才标记为「可接管」。准备完成仍不自动接管，交接窗口需要单独批准。

1. **生产授权可控。** 内部准入、派发及原意图只读核对已接线，隔离 MySQL/Redis 竞态验收通过。正式签发、旧执行者停写证据核对、核查结案和单服务生产门禁仍待完成；精确清理需要另外授权。不得用全局开关放行，也不得复用隔离 CLI 授权。
2. **真机证据可核对。** 用专用非业务资源验证实际云机创建、节点安装与连续上报、DNS 归属、写后读回和所选公共解析器的传播，以及失败后的资源清理。未自然触发重试就记录为未覆盖，不能当成真机重试通过；受控故障注入不是启用这项能力的默认前置，也不在业务节点演练。ICMP 和权威 DNS 读回不能替代真实业务访问检查。
3. **候选部署可回退。** 按[安全发布与回滚流程](safe-deployment.md)固定提交及镜像摘要，保留上一版本、备份和恢复凭证；先在候选环境核对迁移、HTTP/节点回调和后台进程。首次部署不启用写入。后续只用 `redis_failover:machine_failover` 的独立工作器，确认原业务队列健康。独立队列和工作器仍使用现有 Redis，不等同于独立 Redis 服务。
4. **交接对象有基线。** 在获准后的只读核对中记录服务及成员、源机/安装身份、当前 DNS 记录 ID/类型/线路/值/TTL、凭证修订与容量、双方待执行任务、当前线上版本和回退责任人。只保留必要的脱敏摘要；凭证、健康和 DNS 状态到窗口前复核，过期或不明即停止。
5. **交接和回退演练通过。** 以模拟云和 DNS 覆盖无授权、过期、凭证或策略漂移、旧任务迟到、旧执行者尚未停止、写入结果未知和回退后重放。验证批准范围外零写入，停止后零新派发，历史意图和首错仍可核对。不能只验证页面按钮。

## 接管窗口

1. 确认单个目标服务的授权、当前 DNS/节点基线和各项待命关卡。keliboard 保持无写权限；可对比观测结果，但本地观测通过不是切换授权。
2. 由获准操作者暂停 tanzhen 对**该服务**的派发，核清已排队、运行中及结果未知的云和 DNS 操作。同时排除其他自动任务对同一资源的写入。keliboard 的内部锁不约束 tanzhen；不能确认旧执行者已停止写入，便不接管。其他服务继续照常运行。
3. 复核实际 DNS 与节点状态未漂移，再单独授权 keliboard 成为该服务的唯一执行者。只允许已批准的提供商、凭证、机型、候选次数和 DNS 记录；自动轮换、自动开机及其他服务不随交接开启。
4. 在约定观察窗口比对派发审计、云库存、节点健康、权威 DNS 和公共解析结果，并通过实际业务路径检查可用性。出现双写、身份漂移、队列积压影响业务、未知写入或业务探测失败，立即停止该服务的新派发，进入核对或回退。

## 停止与回退

- 先撤销 keliboard 对该服务的新派发并请求停止现有执行。核对队列中的旧任务、租约和回调已不再推进；[运行器](../../../app/Services/ServerMachine/Cloud/MachineFailoverRunner.php)把不确定操作保留为待核查或保留，不把「已停止」当作外部写入已撤销。
- 对已发出或结果未知的云/DNS 请求，仅按原意图、记录 ID 和归属核对现状；不重复创建/删除，不批量清队列，不盲目把 DNS 改回旧地址。当前仍在承载业务的候选机不得清理。
- 若需要恢复旧 DNS，先确认旧节点能正常服务、当前记录归属和新的回退授权，再单独恢复并核验解析与业务。未核清写入或旧节点仍故障时，保留可用入口并转人工处置。
- 仅在确认 keliboard 已停止该服务的写入、待处理外部操作已核实、业务基线清楚后，才把执行权交还 tanzhen。主站镜像回滚与故障转移交还分别验收；不靠重启整个 Horizon 或回滚数据库来恢复执行权。

目前下一步是补齐旧执行者停写证据的核验，以及核查结案后释放接管名额的流程，并继续先在隔离环境验证。正式环境、现有自动开关和 tanzhen 不需要为这项工作做任何改动。
